## 1단계. 프로젝트 초기 설정 (골격 구축)

### 할 일
- [ ] Notion 통합(Integration) 생성 후 토큰 발급
- [ ] `Projects` 데이터베이스 생성 (PRD 5장의 12개 속성), 통합에 DB 연결(Connections) 권한 부여
- [ ] 샘플 데이터 3건 입력 (공개 2건 + 비공개 1건, 대표 1건 이상, 본문에 지원 블록 포함)
- [ ] `apps/api`: `NOTION_TOKEN`, `NOTION_DATABASE_ID`를 `src/config/env.ts`에 zod 스키마로 추가
- [ ] `.env.example` 작성, `.env`가 `.gitignore`에 있는지 확인
- [ ] Notion SDK 설치 (`@notionhq/client`)
- [ ] `npm run dev`로 web(:3000) + api(:4000) 동시 기동 확인
- [ ] 라우트 뼈대 생성: `/`, `/projects`, `/projects/[slug]` (빈 페이지, 한국어 제목만)
- [ ] 헤더 `links` 배열에 `프로젝트` 메뉴 추가

### 왜 이 순서인가
토큰, DB, 환경 변수가 없으면 이후 모든 단계(API 호출, 화면 데이터)가 막힌다. 외부 서비스 설정은 코드로 해결할 수 없는 선행 조건이므로 가장 먼저 처리한다. 샘플 데이터를 일찍 넣어 두면 이후 단계에서 실제 데이터로 바로 검증할 수 있다.

### 예상 소요 시간
약 20분 (Notion 설정 10분, 코드 골격 10분)

### 완료 기준
- Notion API로 DB를 조회하는 스크립트(또는 임시 호출)가 샘플 3건을 반환한다.
- `npm run dev`가 오류 없이 실행되고 세 경로가 모두 열린다.
- `npm run typecheck`, `lint`, `build` 통과
- `.env`가 커밋 대상에 없다.

## 2단계. 공통 모듈/컴포넌트 개발

### 할 일

**API (`apps/api`)**
- [ ] 타입: `Project` 모델(PRD 6.4)과 Notion 응답 → `Project` 변환 매퍼 (`slug` 누락 행 제외)
- [ ] Notion 클라이언트 모듈 (DB 쿼리, 페이지 블록 조회, `공개` 필터는 서버 쿼리 조건으로 강제)
- [ ] 메모리 캐시 유틸 (TTL 60초, Notion 장애 시 마지막 캐시 반환 옵션)
- [ ] 공통 에러/응답 규칙 점검: `asyncHandler`, `HttpError`, `{ data }` / `{ error }` 형식

**웹 (`apps/web`)**
- [ ] 공유 타입 정의 (`Project`) 및 `api()` 래퍼 사용 확인
- [ ] shadcn/ui 추가: `card`, `badge`, `skeleton`, `button` (`cd apps/web && npx shadcn@latest add <이름>`)
- [ ] `ProjectCard` (썸네일, 제목, 한 줄 설명, 기술 스택 배지)
- [ ] 상태 컴포넌트: `ProjectCardSkeleton`, `ErrorMessage`, `EmptyState`("프로젝트가 없습니다")
- [ ] Zustand 스토어 `src/stores/`: 선택된 기술 스택 태그 상태
- [ ] 레이아웃(헤더/푸터), 컨테이너 폭, 반응형 그리드 유틸 (1/2/3열)
- [ ] TanStack Query Provider 설정 확인

### 왜 이 순서인가
목록, 상세, 홈은 모두 같은 카드, 상태 UI, 데이터 모델, 캐시를 재사용한다. 이를 먼저 만들면 3단계에서 중복 없이 화면만 조립하면 된다. 반대로 페이지부터 만들면 같은 코드를 세 번 고치게 된다. 또한 `공개` 필터를 하부 모듈에서 강제하면 비공개 데이터가 노출되는 실수를 구조적으로 막을 수 있다.

### 예상 소요 시간
약 40분 (API 모듈 20분, 웹 컴포넌트 20분)

### 완료 기준
- 매퍼가 샘플 3건을 `Project[]`로 변환하고, 비공개/슬러그 누락 행은 제외한다.
- 캐시 TTL 내 두 번째 호출은 Notion을 호출하지 않는다 (로그로 확인).
- 임시 페이지에서 `ProjectCard`, 스켈레톤, 에러, 빈 상태가 각각 렌더링된다.
- `typecheck`, `lint`, `build` 통과

## 3단계. 핵심 기능 개발 (MVP, P0)

### 할 일

**API**
- [ ] `GET /api/projects` (쿼리 `tag`, `featured`, zod 검증)
- [ ] `GET /api/projects/:slug` (메타데이터 + 본문 블록, 없거나 비공개면 `HttpError(404)`)
- [ ] `GET /api/tags` (사용 중인 기술 스택 목록)
- [ ] `src/routes/index.ts`에 라우터 등록

**웹**
- [ ] F2 프로젝트 목록 `/projects`: 카드 그리드
- [ ] F3 기술 스택 필터: 태그 선택 시 목록 필터링 (Zustand 상태 + 쿼리)
- [ ] F4 프로젝트 상세 `/projects/[slug]`: 본문 블록 렌더링(문단, 제목, 목록, 이미지, 코드, 인용, 구분선), 데모/저장소 링크 버튼(`buttonVariants`)
- [ ] F1 홈 `/`: 자기소개 + 대표 프로젝트 3개 이내
- [ ] F5 공개 제어: 비공개 항목이 목록/상세/태그 어디에도 나오지 않는지 확인
- [ ] F6 로딩/에러/빈 상태를 모든 데이터 화면에 적용
- [ ] 미지원 블록은 건너뛰기

### 왜 이 순서인가
공통 모듈이 준비된 상태에서 사용자 시나리오(PRD 3장)의 핵심 흐름인 "홈 → 목록 → 필터 → 상세"를 완성하는 단계다. API를 먼저 만들고 화면을 붙이는 순서를 지켜야, 화면 작업 중 응답 형식이 바뀌는 재작업을 피할 수 있다. 목록 → 상세 → 홈 순으로 만드는 이유는 홈이 목록의 `featured` 조회와 카드를 재사용하기 때문이다. 이 단계가 끝나면 P1 기능을 얹을 안정된 기반이 생긴다.

### 예상 소요 시간
약 1시간 (API 20분, 목록/필터 15분, 상세 15분, 홈/상태 정리 10분)

### 완료 기준
- PRD 3장의 시나리오 1~4를 실제로 수행할 수 있다.
  - 특히 Notion에서 행 추가 + `공개` 체크 → 캐시 TTL(최대 1~2분) 후 사이트에 반영된다.
  - `공개` 해제 → 목록에서 사라지고 상세는 404가 된다.
- API 각 엔드포인트가 정상/잘못된 입력/존재하지 않는 슬러그에서 올바른 응답 형식을 반환한다.
- 코드 수정 없이 프로젝트 추가/숨김이 가능하다 (PRD 성공 지표).
- `typecheck`, `lint`, `build` 통과

## 4단계. 추가 기능 개발 (P1)

### 할 일
- [ ] 정렬: 최신순 / 직접 지정 순서(`순서` 속성), 목록 UI에 정렬 선택 추가
- [ ] 검색: 제목/요약 대상 검색 (API 쿼리 `q` + zod 검증, 디바운스 입력)
- [ ] 다크 모드: 테마 토글, 시스템 설정 연동, 깜빡임(FOUC) 방지
- [ ] SEO: 페이지별 메타데이터(`generateMetadata`), OG 이미지(썸네일), `sitemap`, `robots`
- [ ] Notion 변경 즉시 반영: Webhook 수신 엔드포인트 + 캐시 무효화 (서명/시크릿 검증 필수)
- [ ] (선택, P2) 경력/학력 타임라인, 연락 폼, RSS는 이 단계 이후 별도 백로그로 관리

### 왜 이 순서인가
P1은 모두 MVP가 정상 동작한다는 전제 위에 얹는 기능이다. 기반이 불안정할 때 추가하면 버그의 원인이 MVP인지 추가 기능인지 구분하기 어렵다. 항목 간에는 정렬 → 검색(목록 API 확장, 같은 코드 영역), 다크 모드 → SEO(독립적), Webhook(캐시 구조가 확정된 뒤 무효화 로직 추가) 순으로, 위험도가 낮고 의존성이 적은 것부터 처리한다.

### 예상 소요 시간
약 1시간 30분 (정렬/검색 30분, 다크 모드 15분, SEO 25분, Webhook 20분)

### 완료 기준
- 정렬과 검색, 태그 필터를 동시에 적용해도 결과가 올바르다.
- 다크/라이트 전환이 새로고침 후에도 유지되고 깜빡임이 없다.
- 상세 페이지 링크를 공유하면 제목과 썸네일 OG 이미지가 표시된다.
- Notion 수정 후 Webhook으로 캐시가 무효화되어 TTL을 기다리지 않고 반영된다. 서명이 틀린 요청은 거부된다.
- 3단계의 MVP 시나리오가 회귀 없이 통과한다.
- `typecheck`, `lint`, `build` 통과

## 5단계. 최적화 및 배포

### 할 일

**최적화**
- [ ] Notion 이미지 URL 만료 대응 (서버 프록시 또는 응답 시점 URL 갱신 중 택일)
- [ ] 이미지 최적화 (`next/image`, 적절한 크기, `alt` 텍스트)
- [ ] 목록 LCP 2.5초 이내 측정 및 개선 (Lighthouse)
- [ ] Notion API 호출 최소화 확인 (목록 호출 횟수, 캐시 적중률)
- [ ] 접근성 점검: 키보드 탐색, 명도 대비, 이미지 대체 텍스트
- [ ] 모바일 우선 반응형(1/2/3열) 실기기 또는 에뮬레이터 확인
- [ ] Notion 장애 시나리오 테스트: 마지막 캐시 반환, 캐시 없으면 오류 안내
- [ ] 보안 점검: 토큰 미노출, helmet/CORS 설정(운영 도메인으로 제한), 시크릿 커밋 여부

**배포**
- [ ] 호스팅 방식 결정 (PRD 11장 미결: Vercel + 별도 API 서버 vs. 단일 배포)
- [ ] 운영 환경 변수 설정 (`NOTION_TOKEN`, `NOTION_DATABASE_ID`, API 주소, CORS 허용 도메인, Webhook 시크릿)
- [ ] 운영 빌드/배포, 도메인 연결
- [ ] 운영 환경에서 시나리오 1~4 최종 확인
- [ ] 홈 자기소개 문구와 대표 프로젝트 확정 (PRD 11장 미결)
- [ ] README에 설정/배포 방법 정리

### 왜 이 순서인가
기능이 확정되기 전에 최적화하면 바뀔 코드를 다듬는 낭비가 된다. 성능, 접근성, 보안은 완성된 화면 기준으로 측정해야 정확하다. 배포는 마지막에 하되, 호스팅 방식은 환경 변수와 CORS 설정에 영향을 주므로 최적화 후반부에 결정하고 곧바로 배포로 이어간다.

### 예상 소요 시간
약 1시간 30분 (최적화/점검 1시간, 배포/최종 확인 30분)

### 완료 기준
- 목록 LCP 2.5초 이내, 이미지 만료로 인한 깨짐 없음
- Notion API 장애 상황에서 사이트가 다운되지 않는다.
- 운영 URL에서 PRD 3장 시나리오 1~4가 모두 동작한다.
- 운영 번들/응답에 Notion 토큰이 노출되지 않는다.
- `typecheck`, `lint`, `build` 통과, README 최신화

## 미결 사항과 결정 시점

| 미결 사항 | 결정 시점 |
|---|---|
| 본문 렌더링 방식 (`react-notion-x` vs. 직접 구현) | 3단계 시작 전 (상세 페이지 구현 방식에 직접 영향) |
| 호스팅 방식 | 5단계 후반 |
| 자기소개 문구, 대표 프로젝트 | 3단계 홈 구현 시 임시값, 5단계에서 확정 |
